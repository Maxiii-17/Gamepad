Gamepad is a separate second-edition Android gamepad for Windows PCs. It replaces manual IP entry with a six-digit pairing code, keeps a private token for automatic reconnects, and streams a complete controller surface to a Python bridge that presents an Xbox 360 pad to PCSX2. The original PhonePad 1 and its server in E:\Consloe are untouched.

Critical finding — release artifact mismatch. The source and README are at 2.1.0+3 and include the new 8 ms input stream, Android Wi-Fi low-latency lock, and DSCP marking. The APK at E:\Gamepad\Gamepad-release.apk is still 2.0.0+2, built 31 Oct 22:21 — before those changes. Rebuild and reinstall before treating this as a finished release.

What is built source and project assets

01

Pair-code onboarding

The PC window shows a six-digit code; the phone submits it over UDP. No IP typing or QR scanning.

02

Token-based reconnect

The server issues a 64-bit token, persists it with the phone's IP, and accepts HELLO on later launches.

03

Complete pad surface

Face buttons, D-pad, both sticks, L1/L2/R1/R2, Select/Start, L3/R3, and PS/Guide.

04

Turbo

Held face buttons and L1/R1 pulse every 65 ms (about 7–8 Hz); other controls stay continuous.

05

Custom layout

Seven clusters can be dragged and scaled 70–135%; normalized positions are saved per phone.

06

Essentials & low latency

Keep-screen-on, immersive landscape, Wi-Fi low-latency lock, DSCP best effort, 8 ms stream, pause in background.

07

PC bridge

Python asyncio server on UDP 7777 drives vgamepad's Xbox 360 controller; a Linux evdev backend is also present.

08

Setup package

Launcher, firewall script, requirements, README, four widget tests, and a release APK.

Scope: an Android client, a Windows/Linux Python bridge, and a PCSX2 XInput path. It is not a cloud service, an iOS app, a multiplayer controller hub, or a replacement for a physical pad in competitive play.

How it works one UDP port, one active pad

Pairing, reconnect, input, and link acknowledgements all travel over UDP 7777. The phone never talks to PCSX2 directly.

→

→

→
Xbox 360 padvgamepad / XInput
→
PCSX2Pad 1 · XInput

Input packet: 16 bytes = 8-byte base (buttons, four axes, sequence, feature flags) + 8-byte paired token. Byte 7 carries the PS/Guide feature flag.

1PC shows a code

The server prints the value stored in paircode.txt.

2Phone submits it

GAMEPAD_PAIR plus six digits, sent to the LAN address.

3Server issues a token

A 64-bit token is generated and saved with the phone IP.

4App starts streaming

IP and token are stored; 16-byte samples go out every 8 ms.

5Link is monitored

ACKs arrive about once per second; 3.5 s without one shows No reply.

README at a glance

Quick start

  1. Install Gamepad-release.apk on the phone.
  2. Run E:\Gamepad\start-server.bat on the PC.
  3. Open the app and enter the six-digit code.
  4. Confirm Sending and the server's Paired Gamepad line.
  5. In PCSX2: Pad 1 → XInput → Xbox 360 Controller for Windows.

Pairing and server files

  • paircode.txt keeps the code across restarts.
  • paired_clients.json stores tokens; 8 clients maximum, oldest evicted.
  • Delete both files to rotate the code and forget phones.
  • Legacy 8-byte packets are ignored unless started with --allow-legacy.
  • Gamepad packets add the PS flag and the 64-bit token.

Controls, layout, turbo

  • LAYOUT opens the editor: drag any of seven clusters, resize 70–135%.
  • Reset all restores defaults; Done saves and survives restarts.
  • TURBO affects held face buttons and L1/R1 only; sticks, D-pad, L2/R2, and menu buttons are unaffected.
  • Essentials: keep screen awake, L3/R3, PS/Guide, immersive landscape.

Status and troubleshooting

  • Only one server can own 7777; PhonePad 1 and 2 cannot run together.
  • Prefer a 5 GHz hotspot, keep the phone charged, disable Wi-Fi adapter power saving.
  • ping the phone: most replies should be under 10 ms.

GAMEPAD_PAIR <code>Phone → PCRequest pairing with the six-digit code shown in the server window.
GAMEPAD_PAIRED <token>PC → PhoneIssue a 64-bit token; the failure reply is GAMEPAD_BAD_CODE.
GAMEPAD_HELLO <token>Phone → PCReconnect with the saved token; the PC replies GAMEPAD_READY.

Latency design in the 2.1 source: a fresh 16-byte sample every 8 ms keeps the Wi-Fi radio warm; a low-latency Wi-Fi lock and DSCP 0xB8 marking are requested; streaming stops when the app leaves the foreground. These are best-effort Android and network hints, not latency guarantees.

Major disadvantages ranked by release risk

Critical

The shipped APK is older than the source

Source and README are 2.1.0+3, but Gamepad-release.apk is 2.0.0+2 and predates the 8 ms stream, Wi-Fi lock, and DSCP work. The APK cannot contain changes made after it was built. This is the single biggest gap between what the project claims and what a user actually installs.

High

The control channel is plaintext and replayable

The 64-bit token is sent in every UDP packet with no encryption, HMAC, nonce, or challenge-response. Anyone able to sniff the hotspot can capture and replay input; tokens are stored in plaintext in paired_clients.json and Android preferences. The six-digit code has no expiry and no rate limit, so online guessing is not prevented by the protocol itself.

High

One controller, and the last phone wins

The server has one virtual pad, one active token, and one client IP. If two phones send input, they overwrite each other. There are no player slots, per-client routing, or multiplayer support, which limits the project to a single-player accessory.

High

Fixed port, driver dependency, setup coupling

UDP 7777 is hard-coded, so PhonePad 1 and Gamepad cannot run together and another app may already own the port. The server needs Python, vgamepad, and the ViGEmBus driver; the Linux backend is untested. start-server.bat falls back to E:\Consloe\.venv, coupling the new edition to the old project directory.

Medium-high

Sideload-only, debug-signed distribution

The release APK uses the Android debug certificate. There is no Play Store listing, no update channel, and no signed release pipeline. Android shows sideload warnings, and users must manually track new versions.

Medium

Limited input fidelity

PS/Guide is not visible through XInputGetState, so it may not reach PCSX2. There is no rumble, L2/R2 are digital 0/255 rather than analog triggers, button remapping and macros are absent, and the turbo rate is fixed at about 7–8 Hz.

Other limitations important, but secondary

  • Latency is best-effort. The 125 Hz stream and Wi-Fi lock help, but DSCP can be ignored; power saving and 2.4 GHz congestion can add 50–100 ms spikes. Continuous streaming also costs battery and airtime.
  • Test depth is thin. Only four widget smoke tests exist. There is no protocol fuzz/replay suite, no end-to-end test, no long soak, and no packet-loss or multi-client coverage.
  • Operational friction. The code appears only in the console, is static until files are deleted, and there is no tray app or log rotation. Eight tokens are kept with FIFO eviction; losing a token means re-pairing.
  • UX gaps. Landscape only, fixed toolbar sizing, no button remapping, limited accessibility labels, and no portrait mode. The center panel can crowd small screens.
  • Documentation drift. server.py still describes 12-byte paired packets although the constant is 16 bytes. The README documents 2.1 low-latency features that are not in the shipped 2.0 APK.
  • No internet play. IPv4 LAN only; no NAT traversal, relay, or IPv6. Both devices must share a hotspot or Wi-Fi subnet.

Recommended next steps

  1. Rebuild and reinstall 2.1.0+3. Replace the APK, confirm versionName 2.1.0 / versionCode 3, and re-run pairing plus the low-latency check.
  2. Authenticate the channel. Add challenge-response or HMAC, rotate/expire tokens, rate-limit pairing, and add per-device revoke. Consider DTLS for confidentiality.
  3. Package the server. Ship a Windows tray/service with bundled Python and ViGEm, a configurable port, and a log file with health state.
  4. Broaden tests. Cover replay, sequence wrap, reconnect, layout persistence, two clients, packet loss, and a 30-minute soak.
  5. Close the input gaps. Add remapping, analog triggers, and rumble; document the PS limitation and publish a support matrix.

Bottom line

Usable today for casual PCSX2 on a trusted hotspot. The pairing flow, pad surface, turbo, keep-awake, and core XInput path work. It is not release-grade until the APK is rebuilt and the plaintext control channel is authenticated. PhonePad 1 remains independent and untouched.
